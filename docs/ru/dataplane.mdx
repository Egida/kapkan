# Плоскость данных в ядре

Любой другой метод подавления атак у Kapkan — это просьба: [RTBH](/docs/mitigation) и
[FlowSpec](/docs/flowspec) просят ваши маршрутизаторы отбрасывать трафик, а [отвод](/docs/scrubbing)
просит их отправить его в другое место. Все три зависят от пира, который готов и способен
выполнить анонс.

Плоскость данных отбрасывает пакеты сама. Kapkan загружает небольшую программу [XDP](/docs/glossary)
в ядро Linux на той машине, где он работает, и правила, которые детектор и так формирует для
FlowSpec, записываются в карты ядра вместо того, чтобы анонсироваться. Ничему не нужно
распространяться, и никакому пиру не нужно это принимать.

<Callout type="warning" title="Он видит только тот трафик, который дошёл до этой сетевой карты">
Фильтр XDP работает с пакетами, которые уже пришли на интерфейс этой машины. Если флуд насытил
аплинк *выше по потоку* от этого узла, канал забит ещё до того, как фильтр увидит хотя бы один
пакет, и локальное отбрасывание ничего не изменит. Именно для этого нужны ступени выше — плоскость
данных является самым точечным ответом в [лестнице эскалации](/docs/escalation), а не заменой
грубым методам.
</Callout>

## Когда это помогает, а когда нет

Это помогает, когда Kapkan работает **в тракте трафика**: на пограничном маршрутизаторе под Linux,
на узле, включённом в разрыв канала (bump-in-the-wire), или на самом атакуемом хосте. Это помогает
и тогда, когда FlowSpec для вас не вариант: многие транзитные провайдеры от него отказываются, а
некоторые маршрутизирующие стеки принимают FlowSpec-маршруты в RIB, не применяя их в плоскости
пересылки, — это выглядит как успех, но не отбрасывает ничего.

Это не помогает, когда Kapkan работает **вне тракта** — классическое развёртывание, при котором
виртуальная машина принимает NetFlow/sFlow от ваших маршрутизаторов и отвечает им по BGP. Через эту
ВМ не проходит атакующий трафик, поэтому отбрасывать ей нечего. В такой топологии плоскость данных
полезна только на отдельном узле очистки, на который BGP-отвод направляет трафик.

## Требования

Четыре вещи, и для каждой — проверка в одну строку:

| Требование | Проверка | Примечания |
| --- | --- | --- |
| Linux 5.15 или новее | `uname -r` | Полный набор тестов прогоняется на 5.15, 6.1, 6.6 и 6.12 при каждом изменении. Debian 12, Ubuntu 22.04/24.04, RHEL 9 и их пересборки подходят. **RHEL/Alma/Rocky 8 — нет**: там 4.18, а поддержка длится до 2029 года, так что проверьте, а не предполагайте. |
| BTF в ядре | `ls /sys/kernel/btf/vmlinux` | Есть в любом дистрибутивном ядре, которое удовлетворяет требованию выше. |
| Смонтированная bpffs | `mount \| grep ' /sys/fs/bpf '` | Kapkan закрепляет (pin) свою программу и карты в `pin_path`, чтобы политика пережила перезапуск процесса. |
| Драйвер сетевой карты с поддержкой XDP | `ethtool -i eth0` и посмотрите драйвер | Необязательно — без него вместо этого используется generic-путь ядра. См. [Режимы подключения](#режимы-подключения). |

Процессу также нужны `CAP_BPF` и `CAP_NET_ADMIN`, чтобы загрузить и подключить программу, право
записи в точку монтирования bpffs и `AF_NETLINK`.

<Callout type="warning" title="Штатный unit systemd по умолчанию их не выдаёт">
Unit systemd для Kapkan намеренно ужесточён и в поставляемом виде блокирует подключение XDP: нет
`AmbientCapabilities`, `ProtectSystem=strict` оставляет `/sys/fs/bpf` только для чтения, а в
`RestrictAddressFamilies` отсутствует `AF_NETLINK`. Это правильное значение по умолчанию: на
большинстве узлов с Kapkan плоскость данных никогда не запускается, и выдавать `CAP_BPF` всем
подряд ради тех немногих, кому она нужна, — плохой размен.

Пакеты поставляют override-файл по пути `/usr/share/kapkan/kapkan-dataplane.conf`. Устанавливайте
его осознанно:

```sh
sudo mkdir -p /etc/systemd/system/kapkan.service.d
sudo cp /usr/share/kapkan/kapkan-dataplane.conf /etc/systemd/system/kapkan.service.d/
sudo systemctl daemon-reload && sudo systemctl restart kapkan
```
</Callout>

Ничто из этого не требует компилятора на узле. Программа BPF компилируется при сборке Kapkan и
поставляется внутри бинарного файла.

## Как это включить

Блок `dataplane` необязателен. Если его нет, функции просто не существует, и бинарный файл ведёт
себя ровно так же, как без неё.

```yaml
dataplane:
  interfaces: [eth0]            # NICs to attach to (at least one; restart to change)
  xdp_mode: auto                # auto | native | generic
  pin_path: /sys/fs/bpf/kapkan  # policy survives a restart of this process
  on_exit: keep                 # keep the program attached on shutdown, or detach
  drop_malformed: false         # unparseable frames pass and are counted

  allowlist:                    # SOURCE prefixes that always pass
    - "198.51.100.7/32"         #   monitoring
    - "192.0.2.0/24"            #   management network

  ratelimit_profiles:           # named ceilings, referenced by static rules
    - { name: icmp_cap, mbps: 10 }
    - { name: dns_reply, pps: 50000 }

  static_rules:                 # always-on operator policy
    - name: drop_chargen
      match: { proto: udp, src_port: 19 }
      action: drop
    - name: cap_icmp
      match: { proto: icmp }
      action: ratelimit
      profile: icmp_cap

  limits:
    max_dynamic_rules: 4096
    max_static_rules: 256
    max_ratelimit_sources: 1048576
```

Затем дайте группе ступень лестницы, которая его использует:

```yaml
hostgroups:
  - name: game-servers
    networks: ["203.0.113.32/27"]
    escalation:
      - { after_seconds: 0,   action: dataplane }   # drop locally first
      - { after_seconds: 120, action: flowspec }    # ask the router if that was not enough
      - { after_seconds: 600, action: blackhole }
```

Строгость возрастает так: `none < dataplane < flowspec < divert < blackhole`, а лестница может
только удерживать или усиливать ответ, поэтому `dataplane` может следовать за ступенью «только
оповещение», но никогда — за `flowspec`, `divert` или `blackhole`. Настроенная ступень без блока
`dataplane` — или с `enabled: false` — отклоняется при запуске, а не молча ничего не делает.

Можно также задать `mitigation: dataplane` как единственный метод группы, без лестницы, — когда
локальное отбрасывание и есть весь нужный вам ответ.

## Что ядро проверяет и в каком порядке

Порядок фиксирован и не настраивается:

1. **Белый список источников** — `dataplane.allowlist`. Совпадение сразу пропускается.
2. **Защищаемые назначения** — ваш `protected_whitelist`, зеркалируемый в ядро. Совпадение сразу
   пропускается.
3. **Статические правила** — ваша постоянно действующая политика, побеждает первое совпадение.
4. **Динамические правила по источникам** — записи по каждому атакующему, установленные детектором.
5. **Динамические правила по жертве** — правила сопоставления атаки, не более восьми на атаку,
   побеждает первое совпадение.
6. **По умолчанию: пропустить.**

<Callout type="info" title="Два белых списка, две разные оси">
`dataplane.allowlist` — это список **источников**, которым всегда разрешено отправлять.
`protected_whitelist` — это список **назначений**, которые никогда не блокируются. Они не
взаимозаменяемы, и оба применяются в ядре: если бы гарантия для назначений держалась только в
пространстве пользователя, оставалось бы окно, в котором правило, установленное мгновением ранее,
всё ещё могло бы отбросить трафик к защищаемому хосту.
</Callout>

Вердикт по умолчанию — всегда **пропустить**. Нигде в программе нет запрета по умолчанию
(default-deny), нет режима, в котором добавление правила меняет судьбу несовпавшего трафика, и нет
автоматического отбрасывания фрагментов или необычных протоколов. Пакет, который не удалось
разобрать, пропускается и учитывается счётчиком, если только вы не включили это сами через
`drop_malformed: true`. Это исполнитель мер подавления, а не межсетевой экран: он отбрасывает то,
что ему велено отбрасывать, и пересылает всё остальное.

## Статическая политика и сгенерированные правила

**Статические правила** пишете вы: они действуют постоянно, не зависят ни от какой атаки и полезны
для трафика, который вам не нужен никогда (`drop_chargen` выше), и для постоянных потолков
(`cap_icmp`). Имена правил обязательны и должны быть уникальными, поэтому два правила никогда не
смогут незаметно обращаться к одной и той же записи.

**Динамические правила** генерируются для каждой атаки из той же классификации, которая питает
FlowSpec: протокол, отражённый порт источника для вектора усиления (amplification), флаги TCP SYN,
фрагментация и доминирующие источники атакующих из выборки трафика. Вы их не пишете и не можете
редактировать; они видны в `/api/v1/bans` у той блокировки, которой принадлежат, и истекают
вместе с ней.

Перезагрузка конфигурации заменяет статическую политику атомарно: Kapkan строит новый набор правил
рядом с действующим и переключается между ними одной записью, поэтому ни один пакет никогда не
проверяется по наполовину применённой политике.

Чего нельзя изменить под работающей программой — так это всего, что подключает объекты ядра или
задаёт их размер: `interfaces`, `xdp_mode`, `pin_path`, `on_exit`, `limits` и самого `enabled`.
Перезагрузка, затрагивающая любой из них, отклоняется целиком, и остаётся активной предыдущая
конфигурация, — так что ради них перезапускайте процесс, а белый список, статические правила и
профили рассчитывайте перезагружать на месте.

## Ограничение скорости по каждому источнику

Действие ограничения скорости здесь применяется **к каждому адресу источника**, а не ко всему
трафику жертвы целиком. У каждого атакующего своё ведро токенов, поэтому лимит в *N* пакетов в
секунду означает, что на *N* удерживается каждый отдельный источник: распределённый флуд
ограничивается по каждому участнику, а не получает права делить один общий потолок на всех.

Этого BGP FlowSpec структурно выразить не может. FlowSpec-атрибут `traffic-rate` применяется к
потоку, который сопоставляет правило, поэтому правило, покрывающее жертву, ограничивает скорость
всего совпадающего трафика этой жертвы совокупно, и легитимные клиенты конкурируют с атакующими за
одну и ту же квоту. Там, где это различие важно, плоскость данных применяет политику, которую ваши
маршрутизаторы применить не могут.

`max_ratelimit_sources` ограничивает, сколько вёдер источников существует одновременно. Это таблица
с вытеснением давно не использовавшихся записей (LRU): за пределом лимита наименее активные
источники вытесняются, а значит, при очень широком флуде часть источников ненадолго проходит снова,
прежде чем их опять ограничат.

## Dry-run

[Dry-run](/docs/safety) распространяется на плоскость данных ровно так же, как на BGP, и
проверяется до того, как что-либо доходит до ядра: пока `dry_run: true`, ни одно правило не
устанавливается и ни один пакет не отбрасывается. Правила, которые Kapkan *установил бы*, пишутся в
лог и видны у блокировки в `/api/v1/bans`, поэтому вы можете сверить их с реальными атаками,
прежде чем включать применение.

## Правила атаки истекают внутри ядра

Каждое сгенерированное правило несёт собственную метку времени истечения, и программа в ядре
считает истёкшее правило отсутствующим. Так сделано намеренно, и на этом многое держится: если
процесс Kapkan умрёт, будет убит или зависнет, установленные им правила всё равно перестанут
действовать в срок. Мёртвая плоскость управления не может оставить легитимный трафик жертвы
отбрасываемым бесконечно.

При штатном завершении работы то, что останется, определяет `on_exit`. Значение по умолчанию,
`keep`, оставляет программу подключённой, поэтому ваша статическая политика продолжает действовать
через перезапуск или обновление, а динамические правила устаревают сами. `detach` снимает программу
полностью, и тогда проходит весь трафик.

## Режимы подключения

Ядро может выполнять программу в двух местах, и разница в том, где именно на пути приёма она
находится:

- **native** — драйвер вызывает её по мере того, как пакеты сходят с сетевой карты, ещё до того,
  как ядро выделит для них `sk_buff`. Требуется поддержка со стороны драйвера.
- **generic** — ядро вызывает её после того, как `sk_buff` уже выделен. Работает на любом
  интерфейсе, включая virtio, и тратит на каждый пакет больше работы, чтобы туда добраться.

`xdp_mode: auto` (значение по умолчанию) использует native там, где драйвер это поддерживает, и
generic там, где нет. `native` отказывается стартовать, а не откатывается, — именно это вам и
нужно, если вы рассчитывали ёмкость под драйверный хук и предпочитаете узнать о проблеме при
загрузке. `generic` принудительно включает второй режим; он полезен в основном под virtio и в
тестовых средах.

<Callout type="warning" title="Откат происходит молча">
При `auto` смена драйвера, обновление ядра или переезд на другую сетевую карту могут перевести вас
с native на generic без единой ошибки. Фактически используемый режим показывает
`kapkan dataplane status`, и он же экспортируется как метрика: проверяйте его после любого
изменения на узле и настройте по нему оповещение, если вы рассчитывали ёмкость под native.
</Callout>

## Что он блокирует, по измерениям

Каждый релиз прогоняет восемнадцать записей атак сквозным образом: синтетическая телеметрия идёт в
настоящий детектор, настоящий классификатор, порождённые им правила компилируются в настоящие карты
ядра, а затем записанные кадры проигрываются через программу. В каждой записи рядом с атакой идёт
поток легитимного трафика, потому что доля заблокированного трафика без него ничего не измеряет.

| | |
| --- | --- |
| Отброшено атакующего трафика | **100%** на семнадцати записях из восемнадцати; **98,5%** на записи с ограничением скорости по источникам, где каждому атакующему источнику достаётся его первый кадр, прежде чем его ведро опустеет |
| Отброшено легитимного трафика | **ноль**, на всех восемнадцати |
| Отброшено трафика из белого списка | **ноль**, на всех восемнадцати |

Записи покрывают UDP- и SYN-флуды на IPv4 и IPv6, усиление через DNS, NTP, CLDAP, SSDP, memcached и
chargen, ICMP-флуд и флуд фрагментами, TCP-ACK-флуд, смешанный многовекторный набор, «ковровую
бомбардировку» `/24`, флуд источниками, кадры с меткой VLAN и IPv6 с расширенными заголовками.

<Callout type="info" title="Это не показатели пропускной способности">
Доля заблокированного трафика говорит о том, какую часть атаки ловят правила. Она ничего не говорит
о том, сколько трафика способен принять на себя конкретный узел, — это зависит от вашей сетевой
карты, вашего драйвера, вашего процессора и от того, подключилась ли программа в режиме native или
generic. Рассчитывайте развёртывание на собственном оборудовании.
</Callout>

## Единственное, что он не проверяет

Пакет IPv6 может нести цепочку расширенных заголовков перед своим заголовком TCP или UDP. Проход по
этой цепочке стоит программе в ядре инструкций, которых у неё без ограничения не хватит, поэтому
она проходит не более **восьми** — а пакет, несущий больше, **пересылается без проверки хотя бы
одного правила**. Шестидесяти четырёх байт заполнителя достаточно, чтобы такую цепочку собрать.

Так сделано намеренно. Предел разбора, который отбрасывал бы пакеты, был бы запретом по умолчанию,
спрятанным внутри парсера, и одна цепочка, выглядящая некорректно, вывела бы клиента из строя.
Вердикт плоскости данных по умолчанию — всегда «пропустить», и здесь не исключение.

Но это ещё и способ обойти ваш фильтр, поэтому он учитывается и выводится наружу, а не прячется:

```
kapkan_dataplane_filter_bypass_packets_total{reason="ipv6_exthdr_cap"}
```

Легитимный трафик не выстраивает цепочки из восьми расширенных заголовков. **Любое движение этого
счётчика заслуживает внимания**: `kapkan dataplane status` печатает отдельный блок, когда он
ненулевой, а консоль показывает баннер. Если он растёт во время атаки, отбрасывайте или
нормализуйте длинные цепочки расширенных заголовков выше по потоку, где маршрутизатор может сделать
это без бюджета на каждый пакет.

## Лимиты и память

`limits` задаёт размер карт ядра, которые выделяются один раз при подключении программы:

| Ключ | По умолчанию | Что ограничивает |
| --- | --- | --- |
| `max_dynamic_rules` | 4096 | Правила, которые может установить детектор. Каждая блокировка добавляет до 8. |
| `max_static_rules` | 256 | Ваши собственные постоянно действующие правила. |
| `max_ratelimit_sources` | 1048576 | Вёдра токенов по каждому источнику. |

`max_dynamic_rules` должно быть **не меньше** `ban.max_active_bans × 8`; Kapkan отвергает
конфигурацию, где оно меньше, потому что иначе установка правил начнёт срываться в разгар атаки и
молча деградировать до blackhole. Учтите, что значения по умолчанию стоят ровно на этой границе —
при 512 активных блокировках.

Память карт списывается на memory cgroup сервиса (ядро 5.11 и новее), поэтому если вы задаёте
`MemoryMax=` в unit-файле, рассчитывайте его с учётом карт: доминирует таблица вёдер по источникам.

## Устранение неполадок

`kapkan dataplane status` показывает работающую политику: какие интерфейсы подключены, режим
подключения, активное поколение политики, количество правил и счётчики по каждому правилу. Он
читает закреплённое (pinned) состояние напрямую, поэтому работает и тогда, когда демон не
запущен, — это первое, что нужно собрать для любого обращения в поддержку.

Типичные случаи разобраны в разделе [Устранение неполадок](/docs/troubleshooting): программа не
подключается; счётчики растут, а трафик атаки всё равно приходит (обычно это режим generic или
фильтр не на том интерфейсе); переполненная карта правил.
