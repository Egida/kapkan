# Сетевая интеграция (узлы очистки)

<Callout type="warning" title="Это про сетевую обвязку, а не про политику">
[Узел очистки](/docs/scrubbing) отбрасывает атаку в собственном ядре — эта часть является задачей
kapkan и не требует проектирования сети. **Доставка трафика жертвы *к* узлу и чистого трафика
*обратно наружу* — это задача вашей сети**, и именно здесь развёртывания очистки на самом деле идут
не так. Каждый блок команд на этой странице был выполнен на настоящем ядре Linux в лаборатории
сетевой интеграции (`engine/scripts/labnet/`), прежде чем был записан.
</Callout>

Узел очистки запускает [`kapkan scrub`](/docs/cli): ни обнаружения, ни BGP, ни телеметрии. Мозг
[отводит](/docs/scrubbing) трафик жертвы в сторону узла, узел вытягивает правила блокировки из
`GET /api/v1/dataplane/rules` и отбрасывает атаку в [XDP](/docs/glossary), а чистый трафик
реинжектируется в сторону жертвы. Эта страница — про три вещи, которые окружают это:
**как трафик доходит до узла**, **как чистый трафик его покидает** и **как убедиться, что он
действительно фильтрует**.

## Где располагается узел

Две формы, и выбор определяет всё остальное.

- **Вне пути (off-path, BGP divert).** Узел находится рядом с вашей границей. Когда начинается
  атака, мозг анонсирует `/32` жертвы в сторону next-hop узла, так что маршрутизатор туннелирует
  трафик жертвы на узел; узел отбрасывает атаку и реинжектирует остальное. Именно под эту модель
  созданы конфигурация `scrubbing.nodes[]` и действие `divert` — узел втягивается в путь только для
  хостов под атакой и только пока они под ней.
- **В пути (in-path, L2).** Узел включён мостом в канал, который трафик жертвы и так пересекает, так
  что он всё время видит каждый кадр. Ни BGP, ни туннеля; узел фильтрует на канальном уровне.
  Рассуждать о нём проще, но теперь узел — это «горб» на проводе для *всего* трафика, атака это или
  нет.

Большинство операторов начинают вне пути (off-path) — радиус поражения ошибки составляет один
отведённый хост, а не весь канал.

## Вставка на L2 (in-path)

Включите узел мостом между клиентской стороной и стороной шлюза канала. XDP-программа подключается к
**входному (ingress)** порту, и машине вообще не нужен L3-адрес — на L3 она невидима.

```sh
# On the scrub node: bridge the two ports, no IP on the box.
ip link add br0 type bridge
ip link set eth0 master br0      # client side  (XDP attaches here)
ip link set eth1 master br0      # gateway side
ip link set eth0 up; ip link set eth1 up; ip link set br0 up
```

```yaml
# scrub.yaml — the XDP program attaches to the ingress port.
dataplane:
  interfaces: [eth0]
```

Трафик проходит через мост без изменений; XDP-фильтр отбрасывает только то, что совпадает с
правилами мозга. Поскольку L3-хопа нет, нет и изменения MTU, и ни одной из туннельных проблем ниже.

## Отвод вне пути через GRE или IPIP

Когда узел находится вне пути, маршрутизатор инкапсулирует трафик жертвы в туннель до узла. Работают
и GRE, и IPIP; GRE добавляет 24 байта накладных расходов, IPIP — 20.

```sh
# On the router (rA) and the scrub node (rB): a GRE tunnel between their transport addresses.
ip tunnel add gre1 mode gre remote 10.0.2.2 local 10.0.2.1 ttl 255   # on rA
ip tunnel add gre1 mode gre remote 10.0.2.1 local 10.0.2.2 ttl 255   # on rB
ip addr add 10.9.0.1/30 dev gre1 && ip link set gre1 up              # rA
ip addr add 10.9.0.2/30 dev gre1 && ip link set gre1 up              # rB
# Route the victim prefix through the tunnel toward the node.
ip route add 203.0.113.0/24 via 10.9.0.2 dev gre1                    # on rA
```

IPIP устроен так же с `mode ipip`. GRE-туннель поверх транспорта в 1500 байт сообщает MTU 1476;
IPIP сообщает 1480.

<Callout type="error" title="Сбой, который поднимает вас в 3 часа ночи">
Туннель уменьшает MTU пути. Если ICMP «packet too big», который сообщил бы отправителям, что нужно
уменьшить сегменты, где-то на пути отфильтрован — а так бывает очень часто, — симптом характерен и
обманчив: **мелкие запросы и TCP-рукопожатия проходят нормально, а затем любой крупный ответ
застревает.** SSH подключается, но `ls` большого каталога зависает; сайт загружает свой HTML, но не
картинки. Похоже на проблему приложения. Это проблема MSS, и исправление — на туннельных
маршрутизаторах, а не на конечных точках.
</Callout>

### Подрезка MSS — исправление

Перепишите MSS в каждом TCP-`SYN`, пересекающем туннель, до MTU пути туннеля, чтобы оба конца
согласовали сегменты, которые помещаются. Подрезайте на **обоих** туннельных маршрутизаторах, в
**обоих** направлениях:

```sh
# On each tunnel router:
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -o gre1 -j TCPMSS --clamp-mss-to-pmtu
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -i gre1 -j TCPMSS --clamp-mss-to-pmtu
```

В лаборатории загрузка 4 МБ через туннель без подрезки с отфильтрованным ICMP передала **0 байт и
завершилась по таймауту**; с включённой подрезкой та же загрузка завершилась успешно.
`--clamp-mss-to-pmtu` автоматически отслеживает MTU туннеля, так что переживает изменение MTU без
правки.

## Обратный путь

Отведённый трафик доходит до узла; **чистый** трафик должен покинуть его правильным путём — в сторону
жертвы, а не обратно вниз по грязному туннелю. Именно здесь маршрутизация становится асимметричной, а
у асимметричной маршрутизации две ловушки.

### Утечка маршрутов (route-leaking, переносимо) или VRF (новые ядра)

Дайте реинжектированному трафику собственный контекст маршрутизации, чтобы он выходил через чистый
аплинк независимо от основной таблицы. На любом ядре сделайте это через **policy routing** —
выделенную таблицу, выбираемую через `ip rule`:

```sh
# main table: the dirty uplink (where diverted traffic arrives)
ip route add default via 10.30.0.2 dev eth0
# a dedicated table for reinjected traffic: the clean uplink
ip route add default via 10.31.0.2 dev eth1 table 100
# leak the victim's source into it — reinjected clean traffic takes the clean uplink
ip rule add from 203.0.113.0/24 lookup 100
```

В лаборатории `ip route get 8.8.8.8 from 203.0.113.10 iif eth0` затем разрешается через чистый
аплинк (`dev eth1 table 100`), тогда как всё остальное остаётся в основной таблице.
**VRF-устройство** (`ip link add vrf-clean type vrf table 100`, затем подчинить чистый аплинк) даёт
ту же изоляцию как более чистую абстракцию на ядрах, собранных с `CONFIG_NET_VRF`; это та же
таблица, к которой обращаются через устройство, а не через правило.

### rp_filter и асимметричный ответ

Поскольку префикс жертвы отведён, **обратный маршрут** граничного маршрутизатора к жертве указывает
на туннель. Когда ответ жертвы приходит обратно по обычному каналу, строгая фильтрация обратного
пути (`rp_filter=1`) видит, что источник ответа не маршрутизируется обратно через интерфейс, на
который он пришёл, и **молча его отбрасывает.**

```sh
# The trap, and the fix — on the router that sees the asymmetric reply:
sysctl -w net.ipv4.conf.all.rp_filter=1     # strict: DROPS the asymmetric reply
sysctl -w net.ipv4.conf.all.rp_filter=2     # loose:  accepts it if the source is reachable by ANY path
```

Лаборатория подтверждает это напрямую: пакет, чей обратный путь — другой интерфейс,
**отбрасывается** при `rp_filter=1` и **проходит** при `rp_filter=2` (loose) или `0` (выключено).
Используйте **loose** (`2`) на интерфейсах, которые несут асимметричный трафик очистки — она
по-прежнему отвергает действительно немаршрутизируемые (подделанные) источники, но терпит
асимметрию, которую создал ваш отвод. Задавать это по каждому интерфейсу
(`net.ipv4.conf.<iface>.rp_filter`) безопаснее, чем переключать глобально.

## Подтверждение того, что узел фильтрует

Это шаг, который runbook'и «под атакой» делают неправильно: для узла очистки вопрос не «дошёл ли
маршрут до моего маршрутизатора», а **«подключён ли XDP и отбрасывает ли он?»**. Проверьте это на
самом узле — для этого не нужен работающий демон (она читает закреплённые карты):

```sh
kapkan dataplane status
```

Здоровый узел сообщает `ENFORCING on <iface>`, режим подключения и живой счётчик динамических правил.
В полном цикле лаборатории — мозг обнаруживает атаку flowgen, эскалирует до divert, а настоящий агент
`kapkan scrub` вытягивает блокировку — агент подключил XDP, установил правила мозга, а
`kapkan dataplane status` подтвердил, что блоки динамических правил живут в ядре.

Сторона мозга того же вопроса — это [представление Nodes](/docs/dashboard) и
`GET /api/v1/dataplane/nodes`: узел **жив**, потому что продолжает опрашивать правила — опрос
является сигналом живости, а никогда не самоотчёт узла, — так что узел, который появляется в
инвентаре как живой, — это узел, который спрашивает у мозга, что отбрасывать. Если узел перестаёт
опрашивать в течение `scrubbing.stale_after_seconds`, мозг переанонсирует жертву в сторону выжившего
узла или выполняет `on_all_nodes_lost`, когда не осталось ни одного (см. [очистку](/docs/scrubbing)).

<Callout type="note" title="Воспроизведите это сами">
Оснастка, которая проверила каждый рецепт здесь, закоммичена в `engine/scripts/labnet/`:
`plumbing.sh` прогоняет рецепты туннеля, MSS, L2, `rp_filter` и утечки маршрутов в одноразовых
сетевых пространствах имён, а `scrub-loop.sh` прогоняет полный цикл атака → обнаружение → divert →
очистка → отбрасывание с настоящим узлом `kapkan scrub`. Обоим нужен привилегированный контейнер на
ядре с BPF/BTF, GRE и policy routing.
</Callout>
