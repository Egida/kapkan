# Netzwerkintegration (Scrubbing-Knoten)

<Callout type="warning" title="Das ist die Verkabelung, nicht die Policy">
Ein [Scrub-Knoten](/docs/scrubbing) verwirft den Angriff in seinem eigenen Kernel — dieser Teil ist
Aufgabe von kapkan und braucht kein Netzwerkdesign. **Den Verkehr des Opfers *zum* Knoten und den
sauberen Verkehr *wieder heraus* zu bekommen, ist Aufgabe Ihres Netzwerks**, und genau dort gehen
Scrubbing-Deployments tatsächlich schief. Jeder Befehlsblock auf dieser Seite wurde gegen einen
echten Linux-Kernel im Netzwerkintegrations-Labor (`engine/scripts/labnet/`) ausgeführt, bevor er
niedergeschrieben wurde.
</Callout>

Ein Scrub-Knoten führt [`kapkan scrub`](/docs/cli) aus: keine Erkennung, kein BGP, keine
Telemetrie. Das Gehirn [leitet](/docs/scrubbing) den Verkehr eines Opfers zum Knoten um, der Knoten
holt die Regeln des Bans von `GET /api/v1/dataplane/rules` und verwirft den Angriff in
[XDP](/docs/glossary), und der saubere Verkehr wird wieder in Richtung des Opfers eingespeist. Diese
Seite behandelt die drei Dinge, die darum herumliegen: **wie der Verkehr den Knoten erreicht**,
**wie der saubere Verkehr ihn verlässt** und **wie man bestätigt, dass er tatsächlich filtert**.

## Wo der Knoten sitzt

Zwei Formen, und die Wahl bestimmt alles Weitere.

- **Off-path (BGP-Divert).** Der Knoten lebt neben Ihrem Edge. Wenn ein Angriff beginnt, kündigt
  das Gehirn die `/32` des Opfers in Richtung des Next-Hops des Knotens an, sodass der Router den
  Verkehr des Opfers zum Knoten tunnelt; der Knoten verwirft den Angriff und speist den Rest wieder
  ein. Das ist das Modell, für das die `scrubbing.nodes[]`-Konfiguration und die `divert`-Aktion
  gebaut sind — der Knoten wird nur für Hosts unter Angriff in den Pfad gezogen, und nur, solange
  sie es sind.
- **In-path (L2).** Der Knoten ist in eine Verbindung eingebrückt, die der Verkehr des Opfers
  ohnehin durchquert, sodass er ständig jeden Frame sieht. Kein BGP, kein Tunnel; der Knoten filtert
  auf Leitungsebene. Einfacher zu durchdenken, aber der Knoten ist nun ein Hindernis in der Leitung
  für *allen* Verkehr, ob Angriff oder nicht.

Die meisten Betreiber beginnen off-path — der Wirkungsradius eines Fehlers ist ein umgeleiteter
Host, nicht die gesamte Verbindung.

## L2-Insertion (in-path)

Brücken Sie den Knoten zwischen die Client-Seite und die Gateway-Seite einer Verbindung. Das
XDP-Programm hängt sich an den **Ingress**-Port, und die Box braucht überhaupt keine L3-Adresse — sie
ist auf L3 unsichtbar.

```sh
# On the scrub node: bridge the two ports, no IP on the box.
ip link add br0 type bridge
ip link set eth0 master br0      # client side  (XDP attaches here)
ip link set eth1 master br0      # gateway side
ip link set eth0 up; ip link set eth1 up; ip link set br0 up
```

```yaml
# scrub.yaml — the XDP program attaches to the ingress port.
dataplane:
  interfaces: [eth0]
```

Der Verkehr wird unverändert durch die Brücke weitergeleitet; der XDP-Filter verwirft nur das, worauf
die Regeln des Gehirns passen. Weil es keinen L3-Hop gibt, gibt es keine MTU-Änderung und keines der
Tunnelprobleme weiter unten.

## Off-path-Umleitung über GRE oder IPIP

Wenn der Knoten off-path ist, kapselt der Router den Verkehr des Opfers in einen Tunnel zum Knoten.
GRE und IPIP funktionieren beide; GRE fügt 24 Byte Overhead hinzu, IPIP 20.

```sh
# On the router (rA) and the scrub node (rB): a GRE tunnel between their transport addresses.
ip tunnel add gre1 mode gre remote 10.0.2.2 local 10.0.2.1 ttl 255   # on rA
ip tunnel add gre1 mode gre remote 10.0.2.1 local 10.0.2.2 ttl 255   # on rB
ip addr add 10.9.0.1/30 dev gre1 && ip link set gre1 up              # rA
ip addr add 10.9.0.2/30 dev gre1 && ip link set gre1 up              # rB
# Route the victim prefix through the tunnel toward the node.
ip route add 203.0.113.0/24 via 10.9.0.2 dev gre1                    # on rA
```

IPIP ist mit `mode ipip` identisch. Ein GRE-Tunnel über einen 1500-Byte-Transport meldet MTU 1476;
IPIP meldet 1480.

<Callout type="error" title="Der Ausfall, der Sie um 3 Uhr morgens aus dem Bett holt">
Ein Tunnel verkleinert die Pfad-MTU. Wenn das „packet too big"-ICMP, das Sendern mitteilen würde,
ihre Segmente zu verkleinern, irgendwo auf dem Pfad gefiltert wird — und das wird es sehr oft — ist
das Symptom charakteristisch und irreführend: **Kleine Requests und TCP-Handshakes laufen normal
durch, dann bleibt jede große Antwort stehen.** SSH verbindet sich, aber ein `ls` eines großen
Verzeichnisses hängt; die Website lädt ihr HTML, aber nicht ihre Bilder. Es sieht aus wie ein
Anwendungsproblem. Es ist ein MSS-Problem, und die Lösung liegt auf den Tunnel-Routern, nicht auf den
Endpunkten.
</Callout>

### MSS-Clamping — die Lösung

Schreiben Sie die MSS in jedem TCP-`SYN`, das den Tunnel quert, auf die Pfad-MTU des Tunnels herunter,
sodass beide Enden Segmente aushandeln, die passen. Clampen Sie auf **beiden** Tunnel-Routern, in
**beiden** Richtungen:

```sh
# On each tunnel router:
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -o gre1 -j TCPMSS --clamp-mss-to-pmtu
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -i gre1 -j TCPMSS --clamp-mss-to-pmtu
```

Im Labor übertrug ein 4-MB-Download durch einen Tunnel ohne Clamp bei gefiltertem ICMP **0 Byte und
lief in einen Timeout**; mit gesetztem Clamp wurde derselbe Download abgeschlossen. `--clamp-mss-to-pmtu`
verfolgt die Tunnel-MTU automatisch, sodass es eine MTU-Änderung ohne Bearbeitung übersteht.

## Der Rückpfad

Der umgeleitete Verkehr erreicht den Knoten; der **saubere** Verkehr muss ihn auf dem richtigen Weg
verlassen — zum Opfer hin, nicht zurück durch den dirty Tunnel. Hier wird das Routing asymmetrisch,
und asymmetrisches Routing hat zwei Fallen.

### Route-Leaking (portabel) oder VRF (neuere Kernel)

Geben Sie dem wieder eingespeisten Verkehr seinen eigenen Routing-Kontext, sodass er unabhängig von
der Haupttabelle über den sauberen Uplink ausgeht. Auf jedem Kernel geht das mit **Policy-Routing**
— einer dedizierten Tabelle, die per `ip rule` ausgewählt wird:

```sh
# main table: the dirty uplink (where diverted traffic arrives)
ip route add default via 10.30.0.2 dev eth0
# a dedicated table for reinjected traffic: the clean uplink
ip route add default via 10.31.0.2 dev eth1 table 100
# leak the victim's source into it — reinjected clean traffic takes the clean uplink
ip rule add from 203.0.113.0/24 lookup 100
```

Im Labor löst `ip route get 8.8.8.8 from 203.0.113.10 iif eth0` daraufhin über den sauberen Uplink
auf (`dev eth1 table 100`), während alles andere auf der Haupttabelle bleibt. Ein **VRF-Gerät**
(`ip link add vrf-clean type vrf table 100`, dann den sauberen Uplink einsklaven) bietet dieselbe
Isolation als sauberere Abstraktion auf Kerneln, die mit `CONFIG_NET_VRF` gebaut wurden; es ist
dieselbe Tabelle, erreicht über ein Gerät statt über eine Regel.

### rp_filter und die asymmetrische Antwort

Weil das Präfix des Opfers umgeleitet wird, zeigt die **Rückroute** eines Border-Routers zum Opfer
auf den Tunnel. Wenn die Antwort des Opfers auf einer normalen Verbindung zurückkommt, sieht das
strenge Reverse-Path-Filtering (`rp_filter=1`), dass die Quelle der Antwort nicht über das Interface
zurückroutet, auf dem sie ankam, und **verwirft sie stillschweigend.**

```sh
# The trap, and the fix — on the router that sees the asymmetric reply:
sysctl -w net.ipv4.conf.all.rp_filter=1     # strict: DROPS the asymmetric reply
sysctl -w net.ipv4.conf.all.rp_filter=2     # loose:  accepts it if the source is reachable by ANY path
```

Das Labor bestätigt es direkt: Ein Paket, dessen Rückpfad ein anderes Interface ist, wird unter
`rp_filter=1` **verworfen** und unter `rp_filter=2` (loose) oder `0` (aus) **durchgelassen**.
Verwenden Sie **loose** (`2`) auf den Interfaces, die asymmetrischen Scrubbing-Verkehr tragen — es
weist echte nicht routbare (gespoofte) Quellen weiterhin ab, toleriert aber die Asymmetrie, die Ihre
Umleitung erzeugt hat. Es pro Interface zu setzen (`net.ipv4.conf.<iface>.rp_filter`) ist sicherer,
als es global umzuschalten.

## Bestätigen, dass der Knoten filtert

Das ist der Schritt, den Under-Attack-Runbooks falsch machen: Für einen Scrub-Knoten ist „Die Route
hat meinen Router erreicht" nicht die Frage — **„Ist XDP angehängt und verwirft?"** ist es. Prüfen
Sie es auf dem Knoten selbst, der keinen laufenden Daemon braucht (er liest die gepinnten Maps):

```sh
kapkan dataplane status
```

Ein gesunder Knoten meldet `ENFORCING on <iface>`, den Attach-Modus und eine aktive Anzahl
dynamischer Regeln. In der vollständigen Schleife des Labors — ein Gehirn, das einen Flowgen-Angriff
erkennt, zu Divert eskaliert und ein echter `kapkan scrub`-Agent, der den Ban abholt — hängte der
Agent XDP an, installierte die Regeln des Gehirns, und `kapkan dataplane status` bestätigte, dass die
dynamischen Regel-Blöcke live im Kernel liegen.

Die Seite des Gehirns bei derselben Frage ist die [Nodes-Ansicht](/docs/dashboard) und
`GET /api/v1/dataplane/nodes`: Ein Knoten ist **lebendig**, weil er weiterhin nach Regeln pollt — der
Poll ist das Lebendigkeitssignal, niemals der Selbstreport des Knotens — sodass ein Knoten, der im
Inventar als lebendig erscheint, ein Knoten ist, der das Gehirn fragt, was zu verwerfen ist. Wenn der
Knoten für `scrubbing.stale_after_seconds` aufhört zu pollen, kündigt das Gehirn das Opfer in
Richtung eines überlebenden Knotens neu an oder führt `on_all_nodes_lost` aus, wenn keiner
übrigbleibt (siehe [Scrubbing](/docs/scrubbing)).
