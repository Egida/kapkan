# Integración de red (nodos de scrubbing)

<Callout type="warning" title="Esto es la fontanería, no la política">
Un [nodo de scrubbing](/docs/scrubbing) descarta el ataque en su propio kernel — esa parte es
tarea de kapkan y no requiere ningún diseño de red. **Llevar el tráfico de la víctima *hasta* el
nodo, y el tráfico limpio *de vuelta*, es tarea de tu red**, y es donde los despliegues de
scrubbing acaban torciéndose de verdad. Cada bloque de comandos de esta página se ejecutó contra
un kernel Linux real en el laboratorio de integración de red (`engine/scripts/labnet/`) antes de
escribirse aquí.
</Callout>

Un nodo de scrubbing ejecuta [`kapkan scrub`](/docs/cli): sin detección, sin BGP, sin telemetría.
El cerebro [desvía](/docs/scrubbing) el tráfico de una víctima hacia el nodo, el nodo obtiene las
reglas del ban de `GET /api/v1/dataplane/rules` y descarta el ataque en [XDP](/docs/glossary), y el
tráfico limpio se reinyecta hacia la víctima. Esta página trata las tres cosas que rodean eso:
**cómo llega el tráfico al nodo**, **cómo sale de él el tráfico limpio** y **cómo confirmar que
realmente está filtrando**.

## Dónde se ubica el nodo

Dos formas, y la elección lo condiciona todo lo demás.

- **Off-path (desvío BGP).** El nodo vive junto a tu edge. Cuando empieza un ataque, el cerebro
  anuncia el `/32` de la víctima hacia el next-hop del nodo, de modo que el router hace túnel del
  tráfico de la víctima hacia el nodo; el nodo descarta el ataque y reinyecta el resto. Este es el
  modelo para el que están hechos la configuración `scrubbing.nodes[]` y la acción `divert` — el
  nodo se mete en la ruta solo para los hosts bajo ataque, y solo mientras lo están.
- **In-path (L2).** El nodo se puentea en un enlace que el tráfico de la víctima ya cruza, así que
  ve cada trama todo el tiempo. Sin BGP, sin túnel; el nodo filtra a nivel de cable. Más fácil de
  razonar, pero el nodo es ahora un tope en el cable para *todo* el tráfico, sea ataque o no.

La mayoría de operadores empiezan off-path — el radio de impacto de un error es un único host
desviado, no el enlace entero.

## Inserción L2 (in-path)

Puentea el nodo entre el lado del cliente y el lado del gateway de un enlace. El programa XDP se
adjunta al puerto de **ingress**, y la máquina no necesita ninguna dirección L3 — es invisible en
L3.

```sh
# On the scrub node: bridge the two ports, no IP on the box.
ip link add br0 type bridge
ip link set eth0 master br0      # client side  (XDP attaches here)
ip link set eth1 master br0      # gateway side
ip link set eth0 up; ip link set eth1 up; ip link set br0 up
```

```yaml
# scrub.yaml — the XDP program attaches to the ingress port.
dataplane:
  interfaces: [eth0]
```

El tráfico se reenvía por el puente sin cambios; el filtro XDP descarta solo lo que casan las
reglas del cerebro. Como no hay salto L3, no hay cambio de MTU ni ninguno de los problemas de túnel
de más abajo.

## Desvío off-path sobre GRE o IPIP

Cuando el nodo está off-path, el router encapsula el tráfico de la víctima en un túnel hacia el
nodo. GRE e IPIP funcionan ambos; GRE añade 24 bytes de sobrecarga, IPIP 20.

```sh
# On the router (rA) and the scrub node (rB): a GRE tunnel between their transport addresses.
ip tunnel add gre1 mode gre remote 10.0.2.2 local 10.0.2.1 ttl 255   # on rA
ip tunnel add gre1 mode gre remote 10.0.2.1 local 10.0.2.2 ttl 255   # on rB
ip addr add 10.9.0.1/30 dev gre1 && ip link set gre1 up              # rA
ip addr add 10.9.0.2/30 dev gre1 && ip link set gre1 up              # rB
# Route the victim prefix through the tunnel toward the node.
ip route add 203.0.113.0/24 via 10.9.0.2 dev gre1                    # on rA
```

IPIP es idéntico con `mode ipip`. Un túnel GRE sobre un transporte de 1500 bytes reporta MTU 1476;
IPIP reporta 1480.

<Callout type="error" title="El fallo que te despierta a las 3 de la madrugada">
Un túnel encoge la MTU de la ruta. Si el ICMP "packet too big" que le diría a los emisores que
encojan sus segmentos se filtra en cualquier punto de la ruta — y muy a menudo se filtra — el
síntoma es distintivo y engañoso: **las peticiones pequeñas y los handshakes TCP se completan
normalmente, y luego cualquier respuesta grande se atasca.** SSH conecta pero `ls` de un directorio
grande se cuelga; el sitio carga su HTML pero no sus imágenes. Parece un problema de aplicación. Es
un problema de MSS, y la solución está en los routers del túnel, no en los extremos.
</Callout>

### Clamping de MSS — la solución

Reescribe el MSS en cada `SYN` de TCP que cruce el túnel hasta la MTU de ruta del túnel, de modo
que ambos extremos negocien segmentos que quepan. Aplica el clamp en **ambos** routers del túnel,
en **ambas** direcciones:

```sh
# On each tunnel router:
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -o gre1 -j TCPMSS --clamp-mss-to-pmtu
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -i gre1 -j TCPMSS --clamp-mss-to-pmtu
```

En el laboratorio, una descarga de 4 MB por un túnel sin clamp con ICMP filtrado transfirió **0
bytes y expiró**; con el clamp puesto, la misma descarga se completó. `--clamp-mss-to-pmtu` sigue la
MTU del túnel automáticamente, así que sobrevive a un cambio de MTU sin editar nada.

## La ruta de retorno

El tráfico desviado llega al nodo; el tráfico **limpio** tiene que salir de él por el camino
correcto — hacia la víctima, no de vuelta por el túnel sucio. Aquí es donde el enrutamiento se
vuelve asimétrico, y el enrutamiento asimétrico tiene dos trampas.

### Fuga de rutas (route-leaking, portable) o VRF (kernels recientes)

Dale al tráfico reinyectado su propio contexto de enrutamiento para que salga por el uplink limpio
independientemente de la tabla principal. En cualquier kernel, hazlo con **policy routing** — una
tabla dedicada seleccionada por una `ip rule`:

```sh
# main table: the dirty uplink (where diverted traffic arrives)
ip route add default via 10.30.0.2 dev eth0
# a dedicated table for reinjected traffic: the clean uplink
ip route add default via 10.31.0.2 dev eth1 table 100
# leak the victim's source into it — reinjected clean traffic takes the clean uplink
ip rule add from 203.0.113.0/24 lookup 100
```

En el laboratorio, `ip route get 8.8.8.8 from 203.0.113.10 iif eth0` resuelve entonces por el
uplink limpio (`dev eth1 table 100`) mientras todo lo demás se queda en la tabla principal. Un
**dispositivo VRF** (`ip link add vrf-clean type vrf table 100`, y luego esclaviza el uplink limpio)
da el mismo aislamiento como una abstracción más limpia en kernels compilados con `CONFIG_NET_VRF`;
es la misma tabla, alcanzada a través de un dispositivo en vez de una regla.

### rp_filter y la respuesta asimétrica

Como el prefijo de la víctima está desviado, la **ruta inversa** de un router de borde hacia la
víctima apunta al túnel. Cuando la respuesta de la víctima vuelve por un enlace normal, el filtrado
estricto de ruta inversa (`rp_filter=1`) ve que el origen de la respuesta no encamina de vuelta por
la interfaz por la que llegó, y **la descarta en silencio.**

```sh
# The trap, and the fix — on the router that sees the asymmetric reply:
sysctl -w net.ipv4.conf.all.rp_filter=1     # strict: DROPS the asymmetric reply
sysctl -w net.ipv4.conf.all.rp_filter=2     # loose:  accepts it if the source is reachable by ANY path
```

El laboratorio lo confirma directamente: un paquete cuya ruta inversa es una interfaz distinta se
**descarta** con `rp_filter=1` y **pasa** con `rp_filter=2` (loose) o `0` (off). Usa **loose** (`2`)
en las interfaces que llevan tráfico de scrubbing asimétrico — sigue rechazando orígenes realmente
no enrutables (falsificados), pero tolera la asimetría que creó tu desvío. Fijarlo por interfaz
(`net.ipv4.conf.<iface>.rp_filter`) es más seguro que cambiarlo globalmente.

## Confirmar que el nodo está filtrando

Este es el paso que los runbooks de under-attack hacen mal: para un nodo de scrubbing, "la ruta
llegó a mi router" no es la pregunta — **"¿está XDP adjunto y descartando?"** lo es. Compruébalo en
el propio nodo, que no necesita ningún demonio en ejecución (lee los mapas fijados):

```sh
kapkan dataplane status
```

Un nodo sano reporta `ENFORCING on <iface>`, el modo de attach y un recuento de reglas dinámicas en
vivo. En el bucle completo del laboratorio — un cerebro detectando un ataque de flowgen, escalando a
divert y un agente `kapkan scrub` real obteniendo el ban — el agente adjuntó XDP, instaló las reglas
del cerebro, y `kapkan dataplane status` confirmó que los bloques de reglas dinámicas viven en el
kernel.

El lado del cerebro de la misma pregunta es la [vista de Nodos](/docs/dashboard) y
`GET /api/v1/dataplane/nodes`: un nodo está **vivo** porque sigue sondeando reglas — el sondeo es la
señal de vitalidad, nunca el autoinforme del nodo — así que un nodo que aparece en el inventario
como vivo es un nodo que le está preguntando al cerebro qué descartar. Si el nodo deja de sondear
durante `scrubbing.stale_after_seconds`, el cerebro reanuncia la víctima hacia un nodo superviviente,
o ejecuta `on_all_nodes_lost` cuando no queda ninguno (ver [scrubbing](/docs/scrubbing)).
