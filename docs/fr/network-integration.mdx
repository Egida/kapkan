# Intégration réseau (nœuds de scrubbing)

<Callout type="warning" title="C'est la plomberie, pas la politique">
Un [nœud de scrubbing](/docs/scrubbing) supprime l'attaque dans son propre noyau — cette partie
est le travail de kapkan et ne nécessite aucune conception réseau. **Acheminer le trafic de la
victime *jusqu'au* nœud, et faire ressortir le trafic propre, est le travail de votre réseau**, et
c'est là que les déploiements de scrubbing tournent réellement mal. Chaque bloc de commandes de
cette page a été exécuté contre un vrai noyau Linux dans le laboratoire d'intégration réseau
(`engine/scripts/labnet/`) avant d'être consigné ici.
</Callout>

Un nœud de scrubbing exécute [`kapkan scrub`](/docs/cli) : pas de détection, pas de BGP, pas de
télémétrie. Le cerveau [dévie](/docs/scrubbing) le trafic d'une victime vers le nœud, le nœud tire
les règles du ban depuis `GET /api/v1/dataplane/rules` et supprime l'attaque en
[XDP](/docs/glossary), et le trafic propre est réinjecté vers la victime. Cette page traite des
trois choses qui entourent cela : **comment le trafic atteint le nœud**, **comment le trafic propre
en sort**, et **comment confirmer qu'il filtre réellement**.

## Où se place le nœud

Deux formes, et le choix conditionne tout le reste.

- **Hors chemin (divert BGP).** Le nœud vit à côté de votre edge. Lorsqu'une attaque démarre, le
  cerveau annonce le `/32` de la victime vers le next-hop du nœud, de sorte que le routeur tunnelise
  le trafic de la victime jusqu'au nœud ; le nœud supprime l'attaque et réinjecte le reste. C'est le
  modèle pour lequel la configuration `scrubbing.nodes[]` et l'action `divert` sont conçues — le
  nœud n'est tiré dans le chemin que pour les hôtes sous attaque, et seulement pendant qu'ils le
  sont.
- **Sur le chemin (L2).** Le nœud est ponté dans un lien que le trafic de la victime traverse déjà,
  de sorte qu'il voit chaque trame en permanence. Pas de BGP, pas de tunnel ; le nœud filtre au
  niveau du fil. Plus simple à raisonner, mais le nœud est désormais une bosse sur le fil pour
  *tout* le trafic, attaque ou non.

La plupart des opérateurs commencent hors chemin — le rayon d'impact d'une erreur est un seul hôte
dévié, pas le lien entier.

## Insertion L2 (sur le chemin)

Pontez le nœud entre le côté client et le côté passerelle d'un lien. Le programme XDP s'attache au
port d'**ingress**, et la machine n'a besoin d'aucune adresse L3 — elle est invisible en L3.

```sh
# On the scrub node: bridge the two ports, no IP on the box.
ip link add br0 type bridge
ip link set eth0 master br0      # client side  (XDP attaches here)
ip link set eth1 master br0      # gateway side
ip link set eth0 up; ip link set eth1 up; ip link set br0 up
```

```yaml
# scrub.yaml — the XDP program attaches to the ingress port.
dataplane:
  interfaces: [eth0]
```

Le trafic est transféré à travers le pont sans modification ; le filtre XDP ne supprime que ce que
les règles du cerveau font correspondre. Comme il n'y a pas de saut L3, il n'y a pas de changement
de MTU ni aucun des problèmes de tunnel ci-dessous.

## Diversion hors chemin via GRE ou IPIP

Lorsque le nœud est hors chemin, le routeur encapsule le trafic de la victime dans un tunnel vers le
nœud. GRE et IPIP fonctionnent tous deux ; GRE ajoute 24 octets de surcharge, IPIP 20.

```sh
# On the router (rA) and the scrub node (rB): a GRE tunnel between their transport addresses.
ip tunnel add gre1 mode gre remote 10.0.2.2 local 10.0.2.1 ttl 255   # on rA
ip tunnel add gre1 mode gre remote 10.0.2.1 local 10.0.2.2 ttl 255   # on rB
ip addr add 10.9.0.1/30 dev gre1 && ip link set gre1 up              # rA
ip addr add 10.9.0.2/30 dev gre1 && ip link set gre1 up              # rB
# Route the victim prefix through the tunnel toward the node.
ip route add 203.0.113.0/24 via 10.9.0.2 dev gre1                    # on rA
```

IPIP est identique avec `mode ipip`. Un tunnel GRE au-dessus d'un transport de 1500 octets rapporte
un MTU de 1476 ; IPIP rapporte 1480.

<Callout type="error" title="La panne qui vous réveille à 3 h du matin">
Un tunnel réduit le MTU du chemin. Si l'ICMP « packet too big » qui indiquerait aux émetteurs de
réduire leurs segments est filtré quelque part sur le chemin — et il l'est très souvent — le
symptôme est caractéristique et trompeur : **les petites requêtes et les poignées de main TCP
aboutissent normalement, puis toute réponse volumineuse se bloque.** SSH se connecte mais un `ls`
d'un gros répertoire se fige ; le site charge son HTML mais pas ses images. Cela ressemble à un
problème applicatif. C'est un problème de MSS, et le correctif est sur les routeurs de tunnel, pas
sur les extrémités.
</Callout>

### Clampage du MSS — le correctif

Réécrivez le MSS dans chaque `SYN` TCP qui traverse le tunnel jusqu'au MTU du chemin du tunnel, de
sorte que les deux extrémités négocient des segments qui rentrent. Clampez sur les **deux** routeurs
de tunnel, dans les **deux** directions :

```sh
# On each tunnel router:
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -o gre1 -j TCPMSS --clamp-mss-to-pmtu
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -i gre1 -j TCPMSS --clamp-mss-to-pmtu
```

En laboratoire, un téléchargement de 4 Mo à travers un tunnel sans clampage avec l'ICMP filtré a
transféré **0 octet et expiré** ; avec le clampage en place, le même téléchargement a abouti.
`--clamp-mss-to-pmtu` suit automatiquement le MTU du tunnel, de sorte qu'il survit à un changement
de MTU sans modification.

## Le chemin de retour

Le trafic dévié atteint le nœud ; le trafic **propre** doit en repartir de la bonne façon — vers la
victime, pas de nouveau par le tunnel sale. C'est là que le routage devient asymétrique, et le
routage asymétrique comporte deux pièges.

### Fuite de route (portable) ou VRF (noyaux récents)

Donnez au trafic réinjecté son propre contexte de routage afin qu'il sorte par l'uplink propre quel
que soit l'état de la table principale. Sur n'importe quel noyau, faites-le avec du **routage par
politique** — une table dédiée sélectionnée par une `ip rule` :

```sh
# main table: the dirty uplink (where diverted traffic arrives)
ip route add default via 10.30.0.2 dev eth0
# a dedicated table for reinjected traffic: the clean uplink
ip route add default via 10.31.0.2 dev eth1 table 100
# leak the victim's source into it — reinjected clean traffic takes the clean uplink
ip rule add from 203.0.113.0/24 lookup 100
```

En laboratoire, `ip route get 8.8.8.8 from 203.0.113.10 iif eth0` se résout alors via l'uplink
propre (`dev eth1 table 100`) tandis que tout le reste reste sur la table principale. Un **VRF
device** (`ip link add vrf-clean type vrf table 100`, puis asservissez l'uplink propre) offre la
même isolation sous une abstraction plus propre sur les noyaux compilés avec `CONFIG_NET_VRF` ;
c'est la même table, atteinte via un device au lieu d'une règle.

### rp_filter et la réponse asymétrique

Comme le préfixe de la victime est dévié, la **route inverse** d'un routeur de bordure vers la
victime pointe vers le tunnel. Lorsque la réponse de la victime revient par un lien normal, le
filtrage strict du chemin inverse (`rp_filter=1`) constate que la source de la réponse ne route pas
en retour par l'interface par laquelle elle est arrivée, et **la supprime silencieusement.**

```sh
# The trap, and the fix — on the router that sees the asymmetric reply:
sysctl -w net.ipv4.conf.all.rp_filter=1     # strict: DROPS the asymmetric reply
sysctl -w net.ipv4.conf.all.rp_filter=2     # loose:  accepts it if the source is reachable by ANY path
```

Le laboratoire le confirme directement : un paquet dont le chemin inverse est une interface
différente est **supprimé** sous `rp_filter=1` et **passe** sous `rp_filter=2` (souple) ou `0`
(désactivé). Utilisez le mode **souple** (`2`) sur les interfaces qui transportent du trafic de
scrubbing asymétrique — il rejette toujours les sources réellement non routables (usurpées), mais
tolère l'asymétrie que votre diversion a créée. Le définir par interface
(`net.ipv4.conf.<iface>.rp_filter`) est plus sûr que de le basculer globalement.

## Confirmer que le nœud filtre

C'est l'étape que les runbooks « sous attaque » ratent : pour un nœud de scrubbing, « la route a
atteint mon routeur » n'est pas la question — **« XDP est-il attaché et supprime-t-il ? »** l'est.
Vérifiez-le sur le nœud lui-même, qui n'a besoin d'aucun démon en cours d'exécution (il lit les maps
épinglées) :

```sh
kapkan dataplane status
```

Un nœud sain rapporte `ENFORCING on <iface>`, le mode d'attachement, et un nombre de règles
dynamiques en direct. Dans la boucle complète du laboratoire — un cerveau détectant une attaque
flowgen, escaladant vers divert, et un véritable agent `kapkan scrub` tirant le ban — l'agent a
attaché XDP, installé les règles du cerveau, et `kapkan dataplane status` a confirmé que les blocs
de règles dynamiques vivent dans le noyau.

Le côté cerveau de la même question est la [vue Nœuds](/docs/dashboard) et
`GET /api/v1/dataplane/nodes` : un nœud est **vivant** parce qu'il continue d'interroger pour
obtenir des règles — l'interrogation est le signal de vivacité, jamais le rapport que le nœud fait
sur lui-même — de sorte qu'un nœud qui apparaît dans l'inventaire comme vivant est un nœud qui
demande au cerveau quoi supprimer. Si le nœud cesse d'interroger pendant
`scrubbing.stale_after_seconds`, le cerveau réannonce la victime vers un nœud survivant, ou exécute
`on_all_nodes_lost` quand il n'en reste aucun (voir [scrubbing](/docs/scrubbing)).

Le harnais qui a vérifié chaque recette de cette page est versionné dans `engine/scripts/labnet/` :
`plumbing.sh` exécute les recettes de tunnel, MSS, L2, `rp_filter` et fuite de route dans des

</Callout>
